# v0.2 — Event-driven operational Knowledge Graph

## Purpose

Extend the v0.1 deterministic graph + chunk index + LangGraph agent with **actual Kafka-compatible metadata transport** and **accepted Schema Registry versions**. This is a learning lab with runnable, production-shaped boundaries, not a certified enterprise deployment.

## Two independent ingestion paths

The batch seeder retains the earlier synthetic Kafka/pipeline/dbt/BI metadata and Markdown runbooks. This makes graph questions and RAG runnable without Kafka. The incremental projector consumes JSON metadata event envelopes from a Kafka API broker. A demo adapter registers Avro business schemas in Schema Registry, publishes schema-version events and real-shaped OpenLineage COMPLETE events, and publishes a dbt `manifest.json` subset; the stream consumer updates Neo4j atomically.

The **business records** would be Avro encoded in a separate business Kafka topic, but the *metadata events* in `kg.metadata.events` are explicitly JSON envelopes. Schema Registry governs the business event schema, not the envelope. This distinction matters in reviews.

## Domain model

An accepted schema version produces `(KafkaTopic)-[:USES_SUBJECT]->(SchemaSubject)-[:HAS_VERSION]->(SchemaVersion)` and a monotonic `(SchemaSubject)-[:CURRENT_VERSION]->(SchemaVersion)`. A proposed change produces a separate `SchemaProposal`; it is **not** an accepted schema. `LineageRun` records execution status and `EXECUTES` the `Pipeline` entity. A COMPLETE run creates evidence of consumed topics and written datasets. dbt creates `DbtModel-[:READS_FROM]->Dataset` and `DbtModel-[:PRODUCES]->Dataset` edges.

Every source-derived edge retains `source`, `event_id` and `confidence`. Those values are source attribution, *not a statistically calibrated confidence score*. In this lab `confidence=1.0` means it came from a structured event, not that the metadata is universally accurate.

## Delivery semantics and failure handling

- Kafka delivery is **at least once**. Offset commits occur *after* the Neo4j transaction. Network errors or a Neo4j failure terminate the worker without an offset commit, so restarting replays the event.
- `AppliedEvent(id, fingerprint, status)` implements a transactionally atomic inbox checkpoint. The event and all of its projections commit together. Replays of the identical event return `duplicate`; reusing the same event ID with different content raises `EventConflict` and stops ingestion. This gives **exactly-once graph effect per event ID**, *not* end-to-end exactly-once processing.
- Invalid JSON/envelopes/schema-contract violations go to a Kafka dead-letter topic, where the raw payload, offset and error are kept. The source offset commits only after confirming the DLQ publish. DLQ retry automation, IAM, PII scrubbing and data retention are left for production hardening.
- Accepted versions are immutable and `CURRENT_VERSION` moves only if incoming `version > current.latest_version`; old events cannot rewind the pointer. A separate Registry watcher may re-publish on restart before the graph checkpoint catches up; that is safe for state, but generates new observation records.
- dbt snapshots reconcile links for each model present in the snapshot. Full deletion detection for models removed from a manifest, cross-project entity resolution and distributed-scale checkpointing are NOT implemented. Run identity is `namespace + job name + runId`, while pipeline identity uses name for compatibility with v0.1 fixture; in production prefer qualified IDs consistently.

## Schema validation safety

`assess_schema_change()` is a field-level educational heuristic. Only Schema Registry's compatibility API evaluates technical Avro compatibility. The changed phase registers a backward-compatible v2 (adds `channel` with a default), then tests—but **does not register**—a v3 proposal that removes `customer_id` and changes `event_type` to int. Both the Registry result and heuristic are recorded as separate evidence.

## Retrieval contract

The FastAPI `/impact/{subject}` endpoint runs fixed, read-only, parameterized Cypher along the known lineage chain. LangGraph remains the orchestrator for graph/doc/hybrid answers. It augments graph retrieval with this deterministic impact tool when the question names a known subject. The LLM does not generate arbitrary write-capable Cypher. Dataset permissions/tenant isolation need additional work before exposing an agent to real enterprise metadata.

## Current limitations and intended v0.3

This deliberately avoids claiming live Airflow, actual Spark streaming business workloads, paid vector models or Power BI API credentials. OpenLineage events are **schema-shaped sample events**, not emitted by a deployed Airflow integration. The dbt manifest fixture mirrors key `nodes`, `sources` and `depends_on.nodes` fields without invoking dbt. The documentation retrieval still uses local deterministic hash embeddings from v0.1; this demonstrates retriever wiring, not semantic retrieval accuracy. A production step would use proper embedding models, an evaluation corpus and ACL-aware retrieval. Additional next steps: schema subject authentication, TLS, secret management, OpenTelemetry traces, backpressure metrics, replay tools, tombstones, field-level lineage and RBAC/ABAC.
